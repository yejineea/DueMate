# 🍅 DueMate

할 일이 많은 대학생 대신 **"지금 무엇부터 할지"를 정해 주고, 뽀모도로로 바로 집중하게 해 주는** 과제·일정 관리 웹 앱입니다.

| 바로가기 | 주소 |
| --- | --- |
| 웹사이트 | https://yejineea.github.io/DueMate/ |
| 샘플 데이터로 체험 (저장 안 됨) | https://yejineea.github.io/DueMate/?demo |
| 브라우저 테스트 (139건) | https://yejineea.github.io/DueMate/tests.html |

## 실행 방법

- 브라우저만 있으면 됩니다. 설치·회원가입·서버가 필요 없습니다. 위 주소로 들어가거나 `index.html`을 더블클릭하세요.
- 데이터는 이 브라우저에만 저장됩니다. 다른 기기에서는 **설정 → JSON 백업**한 파일을 **JSON 복원**으로 불러오세요.

**처음 5분 사용법**
1. **설정 → 일정**에 수업·알바를 `매주 반복`으로 넣습니다. 공부 가능 시간이 자동으로 계산됩니다.
2. **+ 과제 추가**에서 과목·유형·제목·마감만 넣습니다. 예상 시간은 자동으로 채워집니다.
3. **뽀모도로 탭** 가운데 큰 원의 **▶ 시작**으로 25분 집중합니다.
4. 집중이 끝나면 "이 단계 끝냈나요?"에 답하고, 과제를 다 하면 **완료 처리**를 누릅니다.
5. **토마토 키우기 탭**에서 이번 주에 모은 🍅만큼 자란 토마토를 확인합니다.

## 1. 제작한 것 소개

### 1-1. v1 → v2

시험 기간에는 과제와 시험이 몰려 "무엇부터 할지" 고민하는 데에도 시간이 듭니다. DueMate는 마감까지 남은 시간, 남은 작업량, 수업·알바를 뺀 **실제 공부 가능 시간**을 계산해 지금 할 일을 골라 줍니다. 처음 만든 v1을 직접 써 보니 아쉬운 점이 있었고, v2로 크게 고쳤습니다.

| v1에서 아쉬웠던 점 | v2에서 바꾼 것 |
| --- | --- |
| 첫 화면이 산만해 지금 할 일이 눈에 안 띔 | 첫 화면 = **뽀모도로 탭** (지금 할 일 + 타이머 + 오늘 계획) |
| 공부 가능 시간을 직접 입력 | 일정만 넣으면 **자동 계산** (직접 입력도 가능) |
| 예상 소요 시간을 직접 입력 | 유형·난이도로 **자동 추정**, 실제 작업 시간으로 **보정** |
| 추천을 봐도 바로 시작할 장치가 약함 | 과제별 **뽀모도로 타이머**, 집중 시간 자동 기록 |
| 계속 쓰게 만드는 동기가 없음 | 모은 🍅로 **토마토 키우기**와 배지 |

### 1-2. 탭별 화면과 사용법

#### 🍅 뽀모도로 (첫 화면)

<p align="center"><img src="docs/images/v2-pomodoro.png" width="70%" alt="뽀모도로 탭"></p>

- **지금 할 일**: 오늘 계획의 첫 과제입니다. 옆으로 밀거나 `‹ ›`·`← →`로 다른 과제로 넘깁니다. 위쪽 태그(`8시간 남음` `중요도 높음` `우선 처리`)가 추천 이유입니다.
- **큰 원 = 타이머**: 빨강은 집중, 연두는 휴식이고 버튼은 원 안에 있습니다. 바깥 얇은 링은 `기록 ÷ 예상` 진행률입니다. 타이머는 **과제마다 따로** 돌아서, 다른 과제를 시작하면 앞 타이머는 남은 시간 그대로 멈춥니다.
- **단계**: `단계 1/4 · 다음 단계 ○○ [✓ 끝냄]`. 🍅를 마치면 "이 단계 끝냈나요?"를 묻습니다.
- **오늘 계획(오른쪽)**: 남은 공부 시간을 🍅(25분 집중 + 5분 휴식) 단위로 `15:20–17:55 영어 에세이 🍅×5`처럼 배치합니다. `− +`(개수), `▲ ▼`(순서), `✕`(오늘 제외)로 **직접 고칠 수 있고**, 고친 내용은 오늘만 유지됩니다.

#### 휴대폰

<p align="center"><img src="docs/images/v2-phone.png" width="70%" alt="휴대폰 화면"></p>

탭이 아래쪽 바로 바뀌고 화면이 1단으로 정리됩니다.

### 1-3. 핵심 기능의 원리

**① 우선순위**
- 점수 = 마감 임박도(60) + 작업 압박도(30) + 중요도(20) + 난이도(10)
- 작업 압박도 = 남은 작업 ÷ 마감 전 공부 가능 시간
- 남은 작업 = `min(예상 × (1 − 단계 진행률), 예상 − 기록 시간)`

**② 공부 가능 시간: 자동 계산 / 직접 입력**
```
빈 시간       = 하루 활동 시간(기본 09:00~24:00) − 그날 일정(겹치면 병합)
공부 가능 시간 = min(하루 최대 공부(8h), 빈 시간 − 식사·이동·휴식(3h))
```
- 공부 시간이 빈 시간에 고르게 퍼져 있다고 보고, "지금부터 마감까지"는 남은 빈 시간만큼만 셉니다.
- 직접 입력 모드에서는 요일별 시간을 사용자가 정합니다.

**③ 예상 시간 자동 추정과 실제 작업 시간 보정**
```
예상 시간 = 유형별 기본 시간 × 난이도 계수 × 단계 수 계수 × 내 기록 보정
```
- **유형별 기본 시간**: 보고서 3h · 발표 4h · 코딩 5h · 시험 공부 6h · 시험 8h · 기타 2h
- **난이도 계수**: ×0.6 ~ ×1.6
- **단계 수 계수**: 하위 작업이 보통보다 많으면 늘리고 적으면 줄임 (×0.7 ~ ×1.5)
- **내 기록 보정**: 완료한 과제의 `실제 ÷ 예상`을 유형별로 평균 (×0.5 ~ ×2)
  - 기록이 적을 때는 1배 쪽으로 당겨서 계산합니다.
  - 과제를 완료할 때마다 다시 계산되어, 진행 중인 과제의 예상 시간이 바로 갱신됩니다.

**실제 작업 시간은 어떻게 재나요?** 과제의 작업 기록을 모두 더한 값입니다. 휴식 시간은 넣지 않습니다.

| 상황 | 기록되는 시간 | 🍅 |
| --- | --- | --- |
| 25분 집중을 끝까지 마침 | 25분 | +1 |
| 집중 중에 중지 | 실제로 집중한 시간 (1분 이상) | 그대로 |
| 과제 상세의 `+15분/+30분/+1시간` | 그만큼 (지울 수 있음) | 그대로 |
| 완료할 때 "실제로 얼마나 걸렸나요?"에 입력 | 입력값과 기록의 차이만큼 | 그대로 |

기록이 예상의 절반도 안 되는 과제를 완료하면 실제 시간을 묻습니다. 타이머 밖에서 한 작업 때문에 "빨리 끝냈다"로 잘못 보정되지 않게 하기 위해서입니다.

**④ 오늘 계획**
1. 남은 공부 시간 ÷ 30분 = 오늘 쓸 🍅 수
2. 마감까지 고르게 나눴을 때 "오늘 몫"을 먼저 배정합니다. 오늘 마감인 과제가 가장 먼저입니다.
3. 남는 🍅는 우선순위 순으로 더 줍니다.
4. 빈 시간대에 실제 시각으로 배치합니다.

직접 고친 개수는 고정하고, 나머지만 다시 배정합니다.

**1. 뽀모도로 (계획 → 크게 확장)**

**2. 공부 가능 시간: 자동 계산 / 직접 입력 (계획 → 구현 + 확장)**
- 직접 입력 모드 유지: 사용자가 정한 값을 업그레이드 후 자동값으로 덮어쓰지 않도록, v1에서 직접 입력하던 사용자는 직접 입력 모드로 옮김
- 일정: 매주 시간표 → **하루만·매주·매월을 한 칸에서**
- 과부하 판단: "이번 주(월~일)" → "앞으로 7일" (일요일에 확인하다 발견)

**3. 예상 시간 자동 추정 + 실제 작업 시간 보정 (계획에 없음 → 추가)**

- 사용자 조정: 유형별 초기화, 보정 끄기 (배율 직접 입력은 자동 계산 취지와 맞지 않아 제외)

- 개수·순서·제외·추가를 직접 수정, 오늘만 유지, 자동으로 되돌리기

````markdown
# DueMate TODO 사이클

과제 조건은 세 가지다. ① Todo 리스트로 작업하면서 **처음 계획 대비 바뀐 점을 기록**한다. ② 다 만들고 한 번에 올리지 않고 **일정 간격으로 push**한다. ③ 커밋 메시지에 **커밋한 내용**이 드러나야 한다. 이 스킬은 세 조건을 매 작업마다 빠짐없이 지키기 위한 절차다.

## 1. 항목 고르기

1. `docs/TODO.md`의 "v2 Todo 리스트"에서 아직 체크되지 않은 항목을 고른다.
2. 서로 의존하는 항목은 엔진 → UI 순서로 묶는다. (예: B1~B3 계산 엔진 → B4 설정 화면)
3. 한 사이클은 **커밋 1~2개 분량**으로 자른다. 화면 개편처럼 큰 항목은 쪼갠다.

## 2. 구현 규칙

- 빌드 도구 없이 브라우저에서 바로 실행되어야 한다. `<script>` 태그로 불러오는 전역 함수 스타일(기존 `js/*.js`)을 그대로 따른다.
- 새 파일을 만들면 `index.html`과 `tests.html`의 스크립트 순서에 모두 추가한다.
- 계산 로직은 `now` 같은 시간 인자를 받는 순수 함수로 작성해 테스트할 수 있게 한다.
- 저장 데이터 구조를 바꾸면 `store.js`의 `normalize()`에 v1 데이터 변환을 함께 넣는다.
- 화면 문구는 한국어, 이모지는 최소한으로 쓴다.

## 3. 검증

`browser-verify` 스킬로 다음을 확인한다.

1. 모든 `js/*.js`에 `node --check` 통과
2. `tests.html` 헤드리스 실행 결과 실패 0건 (계산 로직을 바꿨다면 테스트를 먼저 추가)
3. 바뀐 화면을 `?demo&tab=...` 스크린샷으로 직접 열어 보고 깨진 곳이 없는지 확인

검증에서 문제가 나오면 고친 뒤, **무엇이 문제였고 어떻게 바꿨는지**를 4단계 변경 내역에 남긴다.

## 4. TODO 갱신

- 끝난 항목은 `- [x]`로 체크한다. 항목 문장은 처음 계획 그대로 둔다. (계획과 결과를 비교하기 위해)
- 계획과 다르게 된 경우 "v2 Todo 변경 내역" 표에 한 줄 추가한다.
  - `| 날짜 | 항목 | 변경 | 이유 |`
  - 변경 종류: **수정**(계획한 기능을 다르게 구현), **추가**(계획에 없던 항목), **제외**(하지 않기로 함), **테스트 후 변경**(검증에서 발견한 문제로 바뀐 것)
- 새로 생긴 항목은 리스트 맨 아래 해당 그룹에 `(추가)` 표시와 함께 넣는다. 뺀 항목은 지우지 않고 `~~취소선~~`과 `(제외)`를 붙인다.

## 5. 커밋과 push

- 메시지 형식: `<type>: <무엇을 했는지 한국어로>` — type은 `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `style` 중 하나.
- 본문에 바뀐 내용을 2~4줄 bullet로 적는다. 관련 TODO 번호(예: `TODO B1~B3`)를 적는다.
- 코드와 그에 해당하는 TODO 체크는 **같은 커밋**에 넣는다.
- 커밋 2개 이내마다 `git push origin main`으로 올린다. 마지막에 몰아서 push하지 않는다.
- push 후 GitHub Pages 배포 워크플로가 돌기 때문에, push 전 3단계 검증을 반드시 통과시킨다.
- 화면·코드를 바꾼 push 전에는 `index.html`의 `?v=` 버전을 올린다. 브라우저가 css/js를 최대 10분 캐시하므로, 버전을 안 바꾸면 사용자는 새로고침해도 옛 화면을 본다.

## 예시

```
feat: 시간표 기반 공부 가능 시간 자동 계산 엔진

- 활동 시간대에서 고정 일정을 빼고 생활 시간을 제외해 요일별 공부 가능 시간 산출
- 마감 전 가용 시간을 실제 빈 시간 구간으로 계산 (09~24시 균등 가정 제거)
- tests.html에 시간 계산 테스트 8건 추가
TODO B1~B3
```
````

````markdown
# 브라우저 검증

DueMate의 실행 환경은 브라우저로 한정된다. Node에서 돌리는 테스트는 `localStorage`, `document`, 오디오 같은 실제 실행 환경과 다르므로, 테스트와 화면 확인을 **실제 Chrome 엔진**으로 한다. 사람이 브라우저를 열어 클릭하지 않아도 되도록 헤드리스 모드를 쓴다.

## 준비물

- Chrome: 기본 경로 `C:/Program Files/Google/Chrome/Application/chrome.exe` (다르면 `CHROME` 환경변수로 지정)
- Node: `node --check` 문법 검사용
- 앱 쪽 훅
  - `tests.html`: 로드되면 테스트를 실행하고 `<body data-result="pass|fail">`와 `#summary`에 결과를 쓴다.
  - `index.html?demo`: 샘플 데이터를 메모리에만 올리는 데모 모드 (사용자 데이터를 건드리지 않음)
  - `index.html?demo&tab=<탭>`: 특정 탭으로 바로 연다. `&pomo`를 붙이면 뽀모도로가 진행 중인 상태로 연다.
  - `&at=15:00`: 데모의 시계를 그 시각으로 옮긴다. 밤에 찍어도 오늘 계획이 비지 않게 README 스크린샷은 이 값으로 찍는다. `&theme=dark`는 다크 모드, `&form`은 과제 추가 화면, `&open`은 첫 과제를 펼친 화면.

## 사용법

Bash에서 저장소 루트 기준으로 실행한다.

```bash
# 1) 문법 검사 + 테스트
bash .claude/skills/browser-verify/verify.sh test

# 2) 스크린샷 한 장: 이름, 쿼리, (선택) 높이
bash .claude/skills/browser-verify/verify.sh shot pomodoro "demo&tab=pomodoro"

# 3) README용 전체 탭 스크린샷 (docs/images/v2-*.png)
bash .claude/skills/browser-verify/verify.sh shots

# 4) 휴대폰 폭(390px) 확인: 탭 3개를 나란히 한 장으로
bash .claude/skills/browser-verify/verify.sh phone "pomodoro todo settings"
```

- 헤드리스 Chrome은 창 너비를 약 500px보다 줄이지 못한다. `--window-size=400`으로 찍으면 500px로 그린 뒤 잘라 보여 주므로 "가로로 넘친다"고 오판하기 쉽다. 휴대폰 화면은 반드시 `phone`(390px iframe)으로 확인한다.

- `test`는 실패한 테스트 이름과 메시지를 출력하고, 실패가 있으면 종료 코드 1을 돌려준다.

## 판단 기준

- 테스트는 통과했는데 스크린샷이 이상하면(겹침, 빈 화면, 잘림) 화면 버그로 보고 고친다.
````

## 5. 느낀점과 결론

### 느낀점

- **계획은 16개였지만 끝나고 보니 64개였다.** 써 보고 화면을 보면서 계획이 계속 바뀌었습니다. 바뀔 때마다 이유를 남겨 두니, 지금 "왜 이렇게 됐는지"를 모두 설명할 수 있습니다.
- **자동화의 목표는 '대신 결정하기'가 아니라 '결정을 쉽게 하기'였다.** 만들면서, 공부하는 사람은 결국 사용자 본인이고 자동 계산이 그날의 사정까지 알 수는 없다는 생각에 이르렀습니다. 사용자가 정한 값을 앱이 말없이 덮어써서도 안 된다고 판단했습니다. 그래서 **자동 계산은 출발점이고 최종 결정은 사용자에게 둔다**는 원칙으로 바꾸고, 모든 자동 기능에 직접 수정·되돌리기·끄기를 두었습니다.
- **측정할 수 있는 것과 없는 것을 구분해야 한다.** 앱은 타이머로 잰 시간만 압니다. 계산이 정교해도 입력되는 데이터가 틀리면 결과가 틀리기 때문에, 실제 시간을 확인하고 직접 기록하는 기능으로 보완했습니다.
- **검증 방법이 결과물의 질을 정한다.** 빈 화면, 휴대폰에서 사라진 타이머, 밤에만 실패하는 테스트는 단위 테스트로는 보이지 않았습니다. 실제 브라우저, 실제 화면, 다른 시간대에서 확인할 때만 드러났습니다.

### 방법론: 요구사항 기반 바이브 코딩 + Todo 사이클

`PRD·Todo → AI가 작은 단위로 구현 → 브라우저 테스트·스크린샷 검증 → 직접 써 보고 피드백 → 변경 내역 기록`을 반복했습니다.

- **장점**
  - **속도**: 피드백에서 반영까지 몇 분이면 되어 하루 안에 수십 번 고칠 수 있었습니다.
  - **추적성**: 스킬로 절차를 고정하니 커밋, Todo, 변경 내역이 항상 함께 갱신되었습니다.
  - **안정성**: 매 커밋 테스트를 돌려서 이미 되던 기능이 깨지지 않았습니다.
  - **외부 시선**: 코드 리뷰로 내가 놓친 경우를 찾았습니다.
- **단점**
  - **모호한 요청은 여러 번 왕복합니다.** "더 예쁘게" 같은 요청이 그렇고, 배지만 다섯 번 바뀌었습니다.
  - **부분 수정이 쌓이면 기능이 겹칩니다.** 같은 🍅 차트가 리포트와 성과 탭 두 곳에 생겨 나중에 정리해야 했습니다.
  - **자동화로 확인할 수 없는 부분이 있습니다.** 실기기 알림음, 터치감, 브라우저 캐시는 사람이 직접 써 봐야 압니다.
  - **테스트 자체가 틀릴 수도 있습니다.** 실행 시각에 따라 실패하는 테스트를 고치는 데에도 시간이 들었습니다.
- **개선이 필요한 점**
  - 디자인 요청은 구현 전에 시안 2~3개를 먼저 보여 줍니다. 탭 구성은 이 방식으로 한 번에 정해졌습니다.
  - 피드백 몇 개마다 겹치는 기능을 전체적으로 점검하는 단계를 둡니다.
  - 자동화가 못 보는 항목(실기기·배포 후 화면)은 체크리스트로 따로 확인합니다.
  - 유형별 기본 시간과 보정 방식은 실제 사용자 데이터로 다듬습니다.

### 결론

DueMate v2는 **입력은 줄이고(자동 계산), 실행은 한 번에(첫 화면 타이머), 쓸수록 정확하게(실제 시간 보정), 꾸준함에는 보상을(토마토 키우기)** 주는 방향으로 "무엇부터 할지"의 결정을 쉽게 만들었습니다. 자동으로 계산하되 언제든 직접 고칠 수 있게 한 것이 v1과 가장 큰 차이입니다. 다음에는 PWA로 탭을 닫아도 알림을 받고, 실제 사용자 기록으로 예상 시간 계산을 다듬고 싶습니다.
