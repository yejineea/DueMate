# DueMate

할 일이 많은 대학생 대신 **"지금 무엇부터 할지"를 결정해 주는** 과제·일정 관리 웹 앱입니다.

| 바로가기 | 주소 |
| --- | --- |
| 웹사이트 | https://yejineea.github.io/DueMate/ |
| 샘플 데이터로 체험 (저장 안 됨) | https://yejineea.github.io/DueMate/?demo |
| 브라우저 테스트 (60건) | https://yejineea.github.io/DueMate/tests.html |

## 실행 방법

실행 환경은 **브라우저**입니다. 빌드나 서버 설치가 필요 없습니다.

- 위 웹사이트 주소로 접속하거나, 저장소를 내려받아 `index.html`을 브라우저로 엽니다.
- 처음이라면 `?demo` 주소로 샘플 데이터가 들어간 화면을 먼저 보거나, 설정 탭의 **샘플 데이터 불러오기**를 누르세요.
- 데이터는 브라우저 `localStorage`에 저장되므로 회원가입 없이 바로 쓸 수 있습니다. 설정 탭에서 JSON으로 백업·복원합니다.
- `tests.html`을 열면 핵심 계산과 화면 조작 테스트가 브라우저에서 실행되고 결과가 표시됩니다.

## 1. 제작한 것 소개

시험기간에는 여러 과목의 과제와 시험이 한꺼번에 몰립니다. 해야 할 일이 많을수록 "무엇부터 할지" 고민하는 데에도 시간과 에너지가 듭니다. DueMate는 마감일, 남은 작업량, 중요도, 난이도, 그리고 **실제로 쓸 수 있는 공부 시간**을 함께 계산해서 지금 할 일 하나를 골라 주고, 버튼 하나로 바로 집중을 시작하게 합니다.

10월에 만든 v1을 직접 써 보니 세 가지 문제가 있었습니다. 이번 v2는 이 문제들을 해결하는 데 집중했습니다.

| v1에서 불편했던 점 | v2에서 바꾼 것 |
| --- | --- |
| 첫 화면에 통계 카드, 주간 차트, 4주 차트, 추천, 마감 목록이 한꺼번에 있어 정작 **지금 할 일이 눈에 띄지 않음** | 첫 화면을 **"오늘"** 화면으로 바꿈: 지금 할 일 1개 → 시간대별 오늘 계획 → 핵심 경고만. 통계는 분석 탭으로 이동 |
| 요일별 공부 가능 시간을 **직접 어림잡아 입력**해야 했고, 시간표에 수업을 넣어도 계산에 반영되지 않음 | 하루 활동 시간에서 **시간표와 생활 시간을 빼서 자동 계산**. 마감 전 가용 시간도 실제 빈 시간 구간으로 계산 |
| 추천을 봐도 바로 시작할 장치가 약하고, 스톱워치는 집중 리듬을 잡아 주지 못함 | 추천 과제에서 바로 시작하는 **뽀모도로**. 집중이 끝나면 작업 시간이 자동 기록되어 남은 작업량과 추천 순위가 갱신됨 |

### 핵심 기능

**① 지금 할 일 1개와 이유.** 우선순위 점수(마감 임박도 최대 60 + 작업 압박도 최대 30 + 중요도 20 + 난이도 10)가 가장 높은 과제를 맨 위에 보여 줍니다. 왜 이 과제인지("마감까지 4시간 · 마감 전 가용 시간의 89%가 필요")와 다음 하위 작업도 함께 보여 줍니다.

**② 공부 가능 시간 자동 계산.** 직접 입력하는 대신 아래처럼 계산합니다.

```
빈 시간       = 하루 활동 시간(예: 09:00~24:00) − 수업·알바 시간표(겹치면 병합)
공부 가능 시간 = min(하루 최대 공부 시간, 빈 시간 − 식사·이동·휴식 시간)
예) 샘플 데이터의 월요일: 활동 15h − 수업 5h = 빈 시간 10h → 10h − 생활 3h = 공부 가능 7h
```

공부 가능 시간은 그날의 빈 시간 구간에 고르게 퍼져 있다고 보고, "지금부터 마감까지"의 가용 시간을 구간 단위로 계산합니다. 예를 들어 저녁 6시 반이면 오늘은 남은 빈 시간만큼만 셉니다. 설정 탭에서 요일별 계산 근거(활동·수업/알바·빈 시간·생활·공부 가능)를 표로 확인할 수 있고, 원하면 직접 입력 모드로 바꿀 수 있습니다.

**③ 오늘 계획을 뽀모도로 슬롯으로 배치.** 오늘 남은 공부 시간을 30분(집중 25 + 휴식 5) 단위로 나눈 뒤 두 단계로 배정합니다.
1. 마감까지 고르게 나눠 했을 때 **오늘 해야 하는 몫**을 우선순위 순서로 먼저 배정
2. 남는 뽀모도로는 우선순위가 높은 과제에 남은 작업량만큼 추가

배정된 뽀모도로는 수업 사이 빈 시간에 `19:05–21:40 영어 에세이 🍅×5`처럼 실제 시각으로 배치되고, 4회마다 긴 휴식이 들어갑니다. 오늘 마감인데 시간이 모자라면 몇 개가 부족한지 경고합니다.

**④ 뽀모도로.** 집중 25분 → 짧은 휴식 5분 → … → 4회마다 긴 휴식 15분(길이는 설정 가능). 종료 알림음, 탭 제목 카운트다운(`12:58 집중 · DueMate`), 브라우저 알림을 지원합니다. 집중을 마치면 25분이 과제의 작업 기록에 자동으로 저장되고, 중간에 그만두면 집중한 시간만 기록합니다.

**⑤ 그 밖의 기능 (v1에서 유지).** 과제 CRUD와 하위 작업, 월간/주간 캘린더와 마감 겹침 표시, 7일·4주 과부하 분석, 통계, 평가 항목 기반 성적 계산, 다크 테마, JSON/CSV 내보내기.

### PRD 요약

- **목표 사용자**: 여러 과목의 과제·시험을 병행하며 제한된 시간 안에서 계획을 세워야 하는 대학생

### 4-1. duemate-todo-cycle (직접 제작)

**만든 이유.** 과제 조건 중 지키기 까다로운 것이 세 가지였습니다. ① 처음 계획 대비 바뀐 점을 기록할 것 ② 다 만들고 한 번에 올리지 말고 일정 간격으로 push할 것 ③ 커밋 메시지에 내용을 담을 것. 셋 다 작업에 몰입하다 보면 "나중에 한꺼번에" 하게 되기 쉽습니다. 그래서 이 조건들을 매 작업의 정해진 단계로 만들어 빠뜨리지 않게 했습니다. 특히 "항목 문장은 처음 계획 그대로 두고 변경 내역 표에 따로 적는다"는 규칙 덕분에, 위 3장처럼 계획과 결과를 나란히 비교할 수 있었습니다.

**작업에서 쓰인 방식.**
- v2 커밋은 모두 이 형식(`type: 한국어 요약` + bullet 본문)을 따르고, 기능 커밋에는 관련 TODO 번호를 적었습니다.
- 엔진(B1~B3) → 화면(B4) → 뽀모도로(C1~C3) → 화면 개편(A, C4~C5) → 테스트(D1~D2) → 리뷰 수정(D5) 순서로, 커밋 1~2개마다 push했습니다.
- 검증에서 문제가 나오면 고친 뒤 "테스트 후 변경"으로 기록하는 규칙 덕분에, 9건의 테스트 후 변경이 모두 이유와 함께 남았습니다.

````markdown
---
name: duemate-todo-cycle
description: DueMate 저장소에서 docs/TODO.md의 항목을 하나씩 구현할 때 쓰는 작업 사이클. 항목 선택 → 구현 → 브라우저 검증 → TODO 체크와 "변경 내역" 기록 → 내용이 드러나는 커밋 → 일정 간격 push까지를 한 묶음으로 진행한다. "다음 TODO 진행", "이 기능 구현하고 커밋", "TODO 업데이트" 같은 요청이나 DueMate 기능 추가·수정 작업 전반에 사용한다.
---

# DueMate TODO 사이클

과제 조건은 세 가지다. ① Todo 리스트로 작업하면서 **처음 계획 대비 바뀐 점을 기록**한다. ② 다 만들고 한 번에 올리지 않고 **일정 간격으로 push**한다. ③ 커밋 메시지에 **커밋한 내용**이 드러나야 한다. 이 스킬은 세 조건을 매 작업마다 빠짐없이 지키기 위한 절차다.

## 1. 항목 고르기

1. `docs/TODO.md`의 "v2 Todo 리스트"에서 아직 체크되지 않은 항목을 고른다.
2. 서로 의존하는 항목은 엔진 → UI 순서로 묶는다. (예: B1~B3 계산 엔진 → B4 설정 화면)
3. 한 사이클은 **커밋 1~2개 분량**으로 자른다. 화면 개편처럼 큰 항목은 쪼갠다.

## 2. 구현 규칙

- 빌드 도구 없이 브라우저에서 바로 실행되어야 한다. `<script>` 태그로 불러오는 전역 함수 스타일(기존 `js/*.js`)을 그대로 따른다.
- 새 파일을 만들면 `index.html`과 `tests.html`의 스크립트 순서에 모두 추가한다.
- 계산 로직은 `now` 같은 시간 인자를 받는 순수 함수로 작성해 테스트할 수 있게 한다.
- 저장 데이터 구조를 바꾸면 `store.js`의 `normalize()`에 v1 데이터 변환을 함께 넣는다.
- 화면 문구는 한국어, 이모지는 최소한으로 쓴다.

## 3. 검증

`browser-verify` 스킬로 다음을 확인한다.

1. 모든 `js/*.js`에 `node --check` 통과
2. `tests.html` 헤드리스 실행 결과 실패 0건 (계산 로직을 바꿨다면 테스트를 먼저 추가)
3. 바뀐 화면을 `?demo&tab=...` 스크린샷으로 직접 열어 보고 깨진 곳이 없는지 확인

검증에서 문제가 나오면 고친 뒤, **무엇이 문제였고 어떻게 바꿨는지**를 4단계 변경 내역에 남긴다.

## 4. TODO 갱신

- 끝난 항목은 `- [x]`로 체크한다. 항목 문장은 처음 계획 그대로 둔다. (계획과 결과를 비교하기 위해)
- 계획과 다르게 된 경우 "v2 Todo 변경 내역" 표에 한 줄 추가한다.
  - `| 날짜 | 항목 | 변경 | 이유 |`
  - 변경 종류: **수정**(계획한 기능을 다르게 구현), **추가**(계획에 없던 항목), **제외**(하지 않기로 함), **테스트 후 변경**(검증에서 발견한 문제로 바뀐 것)
- 새로 생긴 항목은 리스트 맨 아래 해당 그룹에 `(추가)` 표시와 함께 넣는다. 뺀 항목은 지우지 않고 `~~취소선~~`과 `(제외)`를 붙인다.

## 5. 커밋과 push

- 메시지 형식: `<type>: <무엇을 했는지 한국어로>` — type은 `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `style` 중 하나.
- 본문에 바뀐 내용을 2~4줄 bullet로 적는다. 관련 TODO 번호(예: `TODO B1~B3`)를 적는다.
- 코드와 그에 해당하는 TODO 체크는 **같은 커밋**에 넣는다.
- 커밋 2개 이내마다 `git push origin main`으로 올린다. 마지막에 몰아서 push하지 않는다.
- push 후 GitHub Pages 배포 워크플로가 돌기 때문에, push 전 3단계 검증을 반드시 통과시킨다.

## 예시

```
feat: 시간표 기반 공부 가능 시간 자동 계산 엔진

- 활동 시간대에서 고정 일정을 빼고 생활 시간을 제외해 요일별 공부 가능 시간 산출
- 마감 전 가용 시간을 실제 빈 시간 구간으로 계산 (09~24시 균등 가정 제거)
- tests.html에 시간 계산 테스트 8건 추가
TODO B1~B3
```
````

### 4-2. browser-verify (직접 제작)

**만든 이유.** 이 앱의 실행 환경은 브라우저로 한정됩니다. 계산 로직을 Node에서 테스트하면 `localStorage`, DOM 이벤트, 오디오처럼 실제 실행 환경에만 있는 부분은 검증할 수 없습니다. 그렇다고 매번 사람이 브라우저를 열어 클릭하면 검증을 건너뛰기 쉽습니다. 그래서 **실제 Chrome 엔진을 화면 없이(헤드리스) 실행**해 테스트 결과와 스크린샷을 명령 한 줄로 얻도록 만들었습니다. 앱 쪽에는 `?demo`(사용자 데이터를 건드리지 않는 샘플 모드)와 `?tab=` 훅을 함께 추가했습니다.

**작업에서 쓰인 방식.**
- 커밋할 때마다 `verify.sh test`로 테스트를 돌렸습니다. 이렇게 잡은 문제: 5일 뒤 마감 과제의 불필요한 부족 경고, 리뷰 회귀 테스트 작성 중 발견한 "23시 마감 과제가 부족 경고에서 빠지는" 버그, `normalize()`가 입력 데이터를 직접 바꾸던 문제.

# 브라우저 검증

DueMate의 실행 환경은 브라우저로 한정된다. Node에서 돌리는 테스트는 `localStorage`, `document`, 오디오 같은 실제 실행 환경과 다르므로, 테스트와 화면 확인을 **실제 Chrome 엔진**으로 한다. 사람이 브라우저를 열어 클릭하지 않아도 되도록 헤드리스 모드를 쓴다.

## 준비물

- Chrome: 기본 경로 `C:/Program Files/Google/Chrome/Application/chrome.exe` (다르면 `CHROME` 환경변수로 지정)
- Node: `node --check` 문법 검사용
- 앱 쪽 훅
  - `tests.html`: 로드되면 테스트를 실행하고 `<body data-result="pass|fail">`와 `#summary`에 결과를 쓴다.
  - `index.html?demo`: 샘플 데이터를 메모리에만 올리는 데모 모드 (사용자 데이터를 건드리지 않음)
  - `index.html?demo&tab=<탭>`: 특정 탭으로 바로 연다. `&pomo`를 붙이면 뽀모도로가 진행 중인 상태로 연다.

## 사용법

Bash에서 저장소 루트 기준으로 실행한다.

```bash
# 1) 문법 검사 + 테스트
bash .claude/skills/browser-verify/verify.sh test

# 2) 스크린샷 한 장: 이름, 쿼리, (선택) 높이
bash .claude/skills/browser-verify/verify.sh shot today "demo&tab=today"

# 3) README용 전체 탭 스크린샷 (docs/images/v2-*.png)
bash .claude/skills/browser-verify/verify.sh shots
```

- `test`는 실패한 테스트 이름과 메시지를 출력하고, 실패가 있으면 종료 코드 1을 돌려준다.
- 스크린샷은 1440px 너비로 찍는다. 찍은 뒤 이미지 파일을 직접 열어 보고 레이아웃이 깨지지 않았는지 확인한다.

### 4-3. code-review (기존 스킬)

**고른 이유.** 직접 만든 테스트는 "내가 떠올린 경우"만 검사합니다. 기능을 다 만든 시점에 내가 생각하지 못한 경우를 찾아 줄 외부 시선이 필요했습니다. `code-review`는 Claude Code에 기본으로 들어 있는 스킬로, 지정한 변경 범위에서 **정확성 버그**를 찾아 "어떤 입력에서 어떻게 틀리는지"까지 보고합니다. 스타일 지적이 아니라 실패 시나리오 중심이라 이번 목적에 맞았고, 설치 없이 바로 쓸 수 있었습니다. 프로젝트에 포함된 파일이 아니라 도구에 내장된 스킬이라 저장소에 SKILL.md 파일은 없습니다. 아래는 스킬 설명입니다.

> Review the current diff, or a PR number/branch/path target, for correctness bugs (plus reuse/simplification/efficiency cleanups where the model's recipe covers them) at the effort level given first, before any target (low|medium|high|xhigh|max: from few high-confidence findings to many, some uncertain; ultra: deep multi-agent review in the cloud). Pass --comment to post findings as inline PR comments, or --fix to apply them to the working tree after the review.

**작업에서 쓰인 방식.** 테스트를 모두 통과한 뒤 v2 전체 변경(`17602e7..HEAD`)을 `medium` 강도로 검토했습니다. 지적 10건을 하나씩 코드로 확인했고 모두 실제 문제였습니다.

## 5. 느낀점과 결론

### 느낀점

**계획은 처음부터 맞을 수 없다.** 처음 Todo 16개는 꽤 꼼꼼하게 세웠다고 생각했지만, 끝나고 보니 추가 5개와 테스트 후 변경 9건이 생겼습니다. 대부분 직접 화면을 보거나 테스트를 돌려 보고서야 알 수 있는 것이었습니다. 예를 들어 "이번 주 작업량" 차트는 계획대로 옮겨 놓고 보니, 작업한 날이 일요일이라 7칸 중 6칸이 이미 지난 날이었습니다. 계획을 고치는 것을 실패가 아니라 정보가 늘어난 것으로 보고, 바뀐 이유를 그때그때 남기니 나중에 설명하기도 쉬웠습니다.

**"자동화"에도 사용자의 결정을 존중하는 경계가 필요하다.** 이번 목표는 공부 시간 입력을 자동화하는 것이었기 때문에, 처음에는 v1 사용자도 모두 자동 계산으로 바꾸려 했습니다. 코드 리뷰에서 "직접 정해 둔 값이 말없이 바뀐다"는 지적을 받고, 직접 바꿔 둔 값이 있는 사용자는 그대로 두도록 바꿨습니다. 편리함을 위한 자동화라도 사용자의 의도를 몰래 덮어쓰면 신뢰를 잃는다는 점을 배웠습니다.

**검증 방법이 결과물의 질을 정한다.** 계산 로직만 테스트했다면 놓쳤을 문제가 많았습니다. 헤드리스 브라우저로 실제 클릭 테스트와 스크린샷을 반복하면서 화면 중복, 겹치는 슬롯, 엉뚱한 버튼 문구를 찾았습니다. 리뷰가 제안한 캐시는 바로 넣는 대신 먼저 측정했고, 21ms라는 숫자를 보고 넣지 않기로 했습니다. "좋아 보이는 개선"보다 "측정된 문제"를 고치는 쪽이 코드를 더 단순하게 지켜 준다는 것을 느꼈습니다.

**AI와 함께 만들 때 사람이 맡을 몫.** 코드 작성 속도는 AI 덕분에 매우 빨랐습니다. 하지만 무엇을 첫 화면에서 뺄지, 경고를 언제 띄울지, 자동화의 경계를 어디에 둘지는 결국 "대학생이 이 화면을 열었을 때 무엇이 필요한가"라는 판단의 문제였습니다. 스킬로 작업 절차를 고정해 두니 AI가 매번 같은 기준으로 검증하고 기록하게 되었고, 사람은 그 판단에 더 집중할 수 있었습니다.

### 결론

DueMate v2는 "무엇부터 할지"라는 결정을 대신해 주는 데 초점을 맞췄습니다. 첫 화면에는 지금 할 일 하나와 오늘 계획만 남겼고, 공부 가능 시간은 시간표만 등록하면 자동으로 계산되며, 버튼 하나로 뽀모도로를 시작하면 집중 시간이 다시 계획에 반영됩니다. 추천, 시간 계산, 실행, 기록이 하나의 흐름으로 이어진 것이 v1과 가장 큰 차이입니다.
